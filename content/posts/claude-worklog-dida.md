我用 Claude Code 之后，逐渐有了一个需求：**知道今天到底干了什么**。不是为了汇报，是因为一周过去以后经常想不起来这几天推进了哪件事。

最直接的做法是读 Claude Code 的转录文件——但它只记录我和模型的对话。而一个做实验的人，一天里大部分时间是在 Word 里改稿、在 Origin 里画图、在 MATLAB 里调参数，这些事在转录里一个字都不会留下。

所以 [claude-worklog-dida](https://github.com/yanghaod2278827/claude-worklog-dida) 用了两个证据源。

## 两个证据源

**一、转录**：从当天的 Claude 会话里抽出我发过的每条消息。这是「我打算做什么」的线索。

**二、文件时间戳**：全盘扫一遍文件的修改和创建时间。第一次全量扫描大约 140 万个文件、70 秒左右，之后会收敛到「热目录」。这是「我实际做了什么」的线索。

两个证据交叉，一条任务才有像样的开始和结束时间。而且文件证据会自动打上 `[human]` / `[likely automated]` 标签——被脚本批量改过的文件不该算成我干的活。

## 编排器不做判断

整个流程每小时跑一次：定时任务 → 抽转录 + 扫文件 → 一次 `claude -p` 调用 → 写回滴答清单的「已完成」→ 再同步进 Obsidian 当天的日记块。

设计上只有一条规则：**编排器不做任何判断，判断全部交给那一次模型调用**，规则写在 `worklog_prompt.zh.md` 里。怎么归类、时间怎么定、哪些算同一件事，都是提示词的事。想改行为就改提示词，不用动代码——这条约束是我在写第二版的时候才想明白的，第一版把一堆启发式规则写进了 Python，结果每调一次都像在做手术。

反向同步也做了：如果我在日记里手写了一条「上午核对了昨天的实验数据」，脚本会把它补成一条已完成的任务，而不是让两种记录各说各话。

## 数字是算出来的

每周日的周总结里，所有统计数字——完成了几件事、各类任务占比、最长的连续工作时段——都由 `weekly_extract.py` 从原始证据直接算，模型只负责写文字。这件事我踩过坑：让模型「总结一下这周的数据」，它给出的数字看着合理，但和原始记录对不上。现在提示词里明确写了「你只能引用脚本算好的数字」。

一次带活动的运行大约花 ¥0.15–0.5，周总结约 ¥0.23。没有活动的整点会在扫描后直接退出，不会调模型。

## 它做不到什么

- 只覆盖**有本地痕迹**的工作。开会、看文献、打电话，除非我写进日记，否则它是看不见的
- Windows only（编排是 PowerShell + 计划任务，Python 部分是跨平台的）
- Claude Code 的转录只保留约 30 天，更早的空档补不回来

我发布这个项目的时候把它标成了 experimental。它解决的只是我一个人的问题，脱离「Windows + 滴答清单 + Obsidian」这套组合，它能提供的价值会打折扣。但如果你刚好也在这套组合里，`-DryRun` 跑一遍大概十分钟就能判断它适不适合你。
