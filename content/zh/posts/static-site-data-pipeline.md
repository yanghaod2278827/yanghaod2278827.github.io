这是[建站那篇](/posts/2026/10/how-this-site-is-built/)的续集。上次只说了"数字由脚本生成"，这次把整条链路拆开：数据从哪抓、什么时候抓、抓失败怎么办。

## 三种数据，三种难度

**GitHub（容易）**：Stars 和项目卡片来自 GitHub API。唯一要处理的是本机 `api.github.com` 被 HTTPS 中间人劫持、Python 的证书库不认——脚本里做了降级：urllib 报证书错误就自动改走 `gh api`。

**豆瓣（中等，要 cookie）**：观影记录要带登录态抓 `movie.douban.com/people/<id>/collect`。这里有两个坑：

- 豆瓣对连续翻页很敏感，实测过整页返回登录壳、抓到 0 条。所以抓取加了 4 小时节流，两次之间不重复翻
- 海报**不能热链**：`img*.doubanio.com` 直连返回 `418 I'm a teapot`，带 referer 也只给约 1KB 的反盗链页面。所以站点上用的是首字母方块，不是海报

**动态（麻烦，要一个服务）**：豆瓣广播、GitHub 活动、B站投稿这些没有 RSS 的地方，靠[自建 RSSHub](https://docs.rsshub.dev)（Docker 一个容器，`127.0.0.1:1200`）转成 JSON 再抓。公共实例直接 403，必须自建。

## 什么时候抓

站点本身是静态的，构建时不联网抓数据——那样每次部署都要等、还可能因对方抽风而失败。做法是**数据先落到本机，再提交进仓库**：

```
本机计划任务 ──抓取──► data/*.json ──有变化才 commit──► GitHub ──push 触发──► 部署
```

两条任务：动态每 2 小时一次，豆瓣观影每天一次（带上面那个 4 小时节流）。都是"数据实质内容没变就不提交"，所以频率再高也不会刷出一堆空 commit。

## 一个必须提前堵的自激循环

第一版上线后出现了一个诡异现象：动态页里开始出现"`yanghaod2278827.github.io` 被推送"这类条目，而且越跑越多。

原因很直白——同步脚本每次提交 `data/activity.json`，就是一次 push；GitHub 活动源把这个 push 当成新动态；下一轮抓取于是有了"新数据"，又提交一次……**每 2 小时转一圈**。

堵法是把本站仓库从 GitHub 源里排除掉。这类循环在"自己观察自己"的系统里很常见，写的时候不容易想到，跑起来才现形。

## 抓失败怎么办

每个脚本都是"抓不到就保留上一份 JSON，打印警告后正常退出"。构建照常进行，页面只是数字停在上一轮——比让整次部署挂掉好得多，尤其是 CI 里那次抓取只是顺手刷新，真正的数据主力在本机。

cookie 会过期，豆瓣那边过期后抓取返回登录页；日志里能看到 `no items scraped`，重新从浏览器取一次 cookie 写进本地文件就行，代码不用动。

## 搜索索引也是构建时生成的

站内搜索没有后端：构建时多输出一份 `index.json`（标题、摘要、正文前 800 字），`/search/` 用它做纯前端过滤。几十篇文章的索引只有几十 KB，不值当上 Elasticsearch。

---

一句话总结这套设计：**抓取是离线的、提交是有变化的、构建是纯静态的**。三者分开，任何一环挂掉都不会连带另外两环。
