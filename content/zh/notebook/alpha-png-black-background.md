## 现象

示意图在看图器和浏览器里显示正常，背景是透明的；插进 Word、或者转成 JPG 之后，透明区域变成一整片纯黑。第一反应通常是「Word 把图渲染坏了」，但同一个文件换个软件打开，黑块还在。

## 根因

`Image.convert('RGB')` 只保留颜色通道，alpha 被直接丢掉。而透明像素的颜色值在文件里通常是 `(0, 0, 0)`——「透明」不是「白色」，丢掉 alpha 之后，看到的就是那些存着的 0。

同一根因还有两个入口：索引色（P 模式）图片的透明存在 `info['transparency']` 里，转 RGB 时同样被丢掉；JPG 格式本身没有 alpha 通道，透明区只能落成某个颜色，通常是黑。所以「转成 JPG」和「convert('RGB')」是同一个错误的两种写法。

## 实证

一张 10×10 的 RGBA 图，左半边完全透明：

```python
im.convert('RGB').getpixel((0, 0))          # (0, 0, 0)      ← 黑块
bg = Image.new('RGB', im.size, 'white')
bg.paste(im, mask=im.split()[-1])
bg.getpixel((0, 0))                          # (255, 255, 255) ← 白底
```

## 修法

```python
from PIL import Image

im = Image.open(src).convert('RGBA')
bg = Image.new('RGB', im.size, 'white')
bg.paste(im, mask=im.split()[-1])
bg.save(dst, 'PNG')
```

`mask` 必须是 alpha 通道本身，省掉它就成了「覆盖」——透明像素的颜色照样被写进去，等于白做。三条配套习惯：交付件里的图统一存 PNG；不要给 Word 塞带 alpha 的 TIFF；批量脚本里禁止出现裸的 `convert('RGB')`。批量场景把这段封成单个函数，所有导出路径都走它——只有一个出口，后面的检查才有意义。

## 为什么看图器正常、Word 里变黑

看图器遇到 alpha 会**先铺一层底**再画图（白底或棋盘格），所以透明区显示为白；Word 拿到的是不透明的 RGB 数据，就直接画那些 0。同一份数据，两种渲染约定，结果一个正常一个全黑——看到的差异不在图里，在看图的程序里。

## 批量检查

单张目检容易漏，而且这类错误往往不是一张、是一批。交付前把 docx/pptx 里的图逐张解出来，统计近黑像素占比，超过阈值就是候选；黑底候选必须为 0。SEM 图本身是黑底、logo 是透明底，这两类走 allowlist 并写明原因——否则检查结果会从「0」变成「很多」，几次之后就没人看告警了。

这一步的价值不在于发现某一张图，而在于**发现「某条生成路径没有走白底合成」**：修的是那个出口，不是那一张图。两次复发的共同点都是新一批图由另一个脚本生成，谁都没错，只是各自实现了一遍转换。

## 判据

看到黑块，先问「透明区被填了什么颜色」，再去怀疑 Word、打印机或显示器。透明是信息，丢掉它必须显式补一个底色。
